## Тесты и покрытие

### 1. Нет автотестов RPC `finalize_yookassa_payment`

- **Severity:** Minor
- **Почему важно:** идемпотентность и атомарность начисления проверяются только ручным чеклистом в README перед живыми платежами; регресс в plpgsql не поймается в CI.
- **Предлагаемое решение:** добавить pgTAP или интеграционные тесты Supabase с пятью кейсами из спеки: первый `succeeded` начисляет; повтор с тем же `provider_payment_id` не удваивает; `canceled` не начисляет; нет строки — ошибка; `succeeded` затем `canceled` не откатывает.

### 2. Неполное покрытие webhook-тестов

- **Severity:** Minor
- **Почему важно:** ошибки валидации входа и граничные статусы YooKassa могут вернуться без сигнала в тестах.
- **Предлагаемое решение:** добавить кейсы 405 и 400 (битый JSON / пустой `object.id`); кейс `succeeded` + `paid !== true`; поправить мок `fetchYookassaPayment`, чтобы учитывал аргумент `id`.

### 3. `createPayment.test.js` не проверяет `Object.keys(body)`

- **Severity:** Minor
- **Почему важно:** регресс с утечкой `amount`/`points` в тело запроса YooKassa не будет пойман.
- **Предлагаемое решение:** добавить assertion на точный набор ключей тела платежа (whitelist полей).

### 4. Нет теста polling-эффекта в `ProfilePage`

- **Severity:** Minor
- **Почему важно:** смена identity `refreshProfile` или `ticksRef` может сломать опрос баланса после возврата с оплаты.
- **Предлагаемое решение:** unit/integration-тест React-эффекта с `?payment=pending` (мок `refreshProfile`, проверка интервала и остановки).

## Поведение

### 5. Загрузка пакетов глотает ошибку PostgREST

- **Severity:** Minor
- **Почему важно:** при сбое API пользователь видит пустую витрину без объяснения — выглядит как «пакетов нет», а не как ошибка.
- **Предлагаемое решение:** в `ProfilePage.jsx` показывать сообщение об ошибке (и опционально retry) вместо тихого пустого списка.

### 6. `payingId` снимается сразу после `window.location.href`

- **Severity:** Minor
- **Почему важно:** на мгновение кнопка снова активна до ухода со страницы — возможен двойной клик и лишний платёж.
- **Предлагаемое решение:** не сбрасывать `payingId` до unload/navigation или держать disabled до полного редиректа.

### 7. `create-payment` не логирует `provider_payment_id` на успехе

- **Severity:** Minor
- **Почему важно:** спека просит это поле в логах для трассировки платежа в support/ops.
- **Предлагаемое решение:** добавить structured log с `provider_payment_id` на успешном пути создания платежа.

## Документация и ops

### 8. Drift стартовых init-миграций

- **Severity:** Minor
- **Почему важно:** в репо и remote разные timestamps init-миграций (не файл `yookassa_payments`); `db push` по-прежнему расходится по истории init.
- **Предлагаемое решение:** отдельная repair-задача: выровнять историю init между локалью и remote (не часть фичи YooKassa).

### 9. `canceled`/`failed` в RPC не sticky

- **Severity:** Minor (осознанное решение)
- **Почему важно:** остаточный риск — `canceled` затем `succeeded` начислит баллы; в спеке так задумано, но стоит явно зафиксировать.
- **Предлагаемое решение:** документировать как принятое пов поведение, не как баг к срочному фиксу; при необходимости — отдельный ADR или комментарий в миграции/RPC.

### 10. CORS `Access-Control-Allow-Origin: '*'` на `create-payment`

- **Severity:** Minor
- **Почему важно:** широкий CORS на JWT-защищённом endpoint — лишняя поверхность; для same-origin SPA не обязателен.
- **Предлагаемое решение:** ограничить origin до `PUBLIC_APP_URL` или убрать явный `*`, если preflight не нужен.

### 11. `refreshProfileRef.current = refreshProfile` в фазе рендера

- **Severity:** Minor
- **Почему важно:** запись ref при render — антипаттерн React; при Strict Mode / concurrent может давать неожиданности.
- **Предлагаемое решение:** перенести присвоение в `useEffect` с зависимостью `[refreshProfile]`.

### 12. `GRANT EXECUTE` на `private.redeem_package` без `auth.uid()`

- **Severity:** Minor
- **Почему важно:** под `service_role` grant бесполезен для клиентского сценария; может вводить в заблуждение при аудите прав.
- **Предлагаемое решение:** уточнить комментарий в миграции или убрать лишний grant, если он не нужен для локалки.

### 13. Чек 54-ФЗ: `buildReceipt` — заглушка

- **Severity:** Minor (follow-up)
- **Почему важно:** до продакшена с фискализацией чек не уходит в YooKassa; это не баг текущей итерации, но блокер для живых платежей при требовании 54-ФЗ.
- **Предлагаемое решение:** отдельный план: реализовать `buildReceipt` в `supabase/functions/_shared/receipt.js` (см. спеку, раздел Follow-up: чек 54-ФЗ).
